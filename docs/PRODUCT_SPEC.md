# USTC Play 产品规格（第一阶段）

## 1. 产品定位

USTC Play 面向中国科学技术大学学生，帮助同学在不必先发起约球的情况下，快速知道附近球场是否热闹、是否可能加入，以及自己关注的同学是否正在运动。首期支持篮球和足球，并以手机浏览器为主要使用场景。

首期是单设备高保真交互原型：不登录、不联网、无真实多人数据。所有可变内容只保存在当前浏览器的 `localStorage`。界面必须清楚说明该边界，不能让用户误以为跨设备或不同用户间已同步。

## 2. 核心信息口径

以下概念必须分开呈现和命名：

| 概念 | 含义 | 首期数据来源 | 页面文案要求 |
| --- | --- | --- | --- |
| 球场热度 | 现场主观热闹程度，五级 | 内置模拟值或当前设备的一次上报 | 标注为“最近 N 人上报”或“模拟数据” |
| 上报人数 | 在指定时间窗口内提交热度的人数 | 内置模拟值；当前设备的上报记录 | 不得称为场上人数 |
| 正在打球 | 对球场内参与者总量的估计 | 内置模拟值 | 明确为“正在打球人数（模拟）”或等效含义 |
| 准备前往 | 计划前往该球场的人数 | 内置模拟值 | 不与上报人数合并 |
| 今晚可能 | 可能参与者意向人数 | 内置模拟值 | 不能暗示已到场 |
| 我的运动状态 | 当前设备拥有者自行选择的状态 | `localStorage` | 私密设置和过期只影响本机演示 |
| 好友状态 | 内置演示资料中该好友允许公开的状态 | 模拟数据 | 必须持续保留“模拟演示”提示 |

特别说明：用户的“正在打球/前往球场”状态不能自动增加或减少球场卡上的“正在打球/准备前往”人数；在第一阶段这两类数据没有真实关联。第二阶段接入多人数据后再设计经过去重、有效期和隐私授权的聚合规则。

## 3. 第一阶段功能优先级

### P0：可完成核心判断与操作

1. 首页可在篮球、足球间切换，显示收藏球场；可切换查看全部。
2. 每张球场卡同时显示热度、最近上报信息、正在打球、准备前往、今晚可能三类人数。
3. 进入球场详情可查看场地信息，选择五级热度、可选现场说明，并发布到当前浏览器。
4. 我的状态可选择六种状态、篮球/足球、可选球场、有效期，并明确状态会到期。
5. 好友页可搜索、按关注关系筛选、关注或取消关注，并以模拟数据展示公开状态。
6. 我的页可编辑昵称、管理收藏、开关状态展示隐私。
7. 移动端底部导航和关键按钮在常见 iPhone 宽度下可操作；所有数据边界可见。

### P1：交互可信度与清晰度

1. 上报后给出明确成功反馈，并在详情和列表反映当前设备上报的热度。
2. 状态更新后“我的”页即时反映；状态过期后显示为隐身或已过期。
3. 收藏、关注、隐私和昵称刷新后仍保留。
4. 搜索无结果、无收藏等空状态可理解且提供下一步。
5. 公开访问的静态部署可使用深链接刷新，不把构建环境 HTTP 200 当作用户可访问的证据。

### P2：首期后再做

1. 真实账号、好友关系与跨设备同步。
2. 球场热度和人数的实时聚合、反刷、审核及过期规则。
3. 校园地图、通知、照片、实时聊天、约球组队。

## 4. 体验与视觉原则

1. iOS 气质：白色主背景、系统字体优先、蓝色主操作、绿色用于积极或已就绪状态、圆角卡片和克制阴影。
2. 首屏应优先回答“哪里能去、现在有多热闹、我能做什么”，不让装饰信息压过人数和热度。
3. 每个非同步动作都要以本机语义表达，例如“已保存在此设备”“模拟数据”，避免“已通知同学”等真实服务承诺。
4. 触控目标建议不小于 44 × 44 CSS px；长文本可换行或省略，不能遮挡导航。
5. 颜色不是唯一状态信息：热度应同时带文字，选中状态应同时有边框、勾选或文字变化。

## 5. 现有实现审查（2026-10-13）

### 已满足

- 页面结构覆盖首页、发现、球场详情、我的状态、好友、我的，中文文案完整。
- 篮球/足球切换、收藏、五级热度、可选现场说明、状态有效期、搜索、关注、昵称和隐私开关均已有本机交互。
- `localStorage`、README、详情页和个人页均说明了单设备模拟数据边界。
- 视觉使用蓝白主色、绿色状态色、圆角卡片、底部五栏导航；CSS 通过 `safe-area-inset-bottom` 为手机底部留出空间。

### 需要 Agent B 优先处理

1. **P0，项目根目录不唯一**：`/workspace` 与 `/workspace/sites/ustc-play` 的源码与 README 哈希相同。部署、GitHub Actions、README 和后续改动统一以现有 Git 仓库 `/workspace/sites/ustc-play` 为规范根目录，避免发布旧副本。
2. **P0，信息口径不够醒目**：卡片的“12 正在打球”“8 准备前往”没有显式标记为模拟总人数，而“3 人说很热闹”是最近上报者。需补充可见说明或更精准标签，防止用户将二者当成同一类自报数据。
3. **P1，上报记录不完整**：当前上报后列表只写“你刚刚上报了热度”，不展示所选现场说明，也不会更新“最近上报人数/分钟”。作为原型可以不模拟真实聚合，但需要在详情中给出“本机最近上报：热度 + 现场情况 + 时间”的确认，且不改变总人数。
4. **P1，状态与隐私解释有歧义**：关闭隐私后个人页显示“状态已隐身或过期”，但用户难以分辨具体原因；建议显示“已对好友隐藏”或“状态已于 HH:mm 过期”。
5. **P1，好友筛选语义**：`关注我`是固定模拟 ID 列表，不随关注操作变化。可保留模拟性质，但应注明“演示数据”，或在第二阶段接入真实关系前避免把它表述为实时关系。
6. **P1，可访问性**：卡片使用 `article` 点击进入详情，键盘不可达；建议改用可聚焦的按钮/链接或加键盘处理。还需在实际设备检查 320px 宽度时五档热度标签是否拥挤。
7. **P1，场地图像**：当前是插画，符合 README 的说明，但视觉参考图期待更接近真实校园场地。若无授权实拍素材，应继续用插画并加“场地示意图”，不可使用无来源校园照片。

## 6. 后续多人架构的产品前置条件

在第一阶段公网链接已由真实用户网络验证可用前，不进入多人实现。进入第二阶段前，产品侧须先确认：学校身份方案、好友关系是否双向、状态可见范围、状态默认有效期、热度有效窗口、重复上报限制、举报与异常处理、以及“人数”是用户自报还是系统估计。
